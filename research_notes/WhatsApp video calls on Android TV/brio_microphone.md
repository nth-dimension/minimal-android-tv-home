# Logitech Brio 300 microphone missing on a Sony BRAVIA Google TV (Android 12): USB-level cause and workarounds

Context, verified on the device by the parent session (not re-verified here): Sony BRAVIA 4K VH21, Google TV, Android 12, MediaTek. `dumpsys usb` shows 046d:0942 "Brio 300" with device class 239/2/1, ONE configuration named "Brio 305", and only two interfaces: VideoControl, and VideoStreaming with 8 alternate settings. There is no class-1 (audio) interface and no ALSA capture card. snd-usb-audio and uvcvideo are loaded. Video streams via Camera2. Project notes also record that earlier the same day the user described the Sony as seeing the Brio as "an external camera plus USB audio". That is a lead worth re-checking, not a verified fact.

## Q1. Does the Brio 300/305 expose its microphone as a USB Audio Class interface on a normal PC? Are there known cases where it is missing?

### Takeaway
Yes. On Linux PCs, every published descriptor dump of 046d:0942 I could get shows FIVE interfaces in one configuration: UVC 1.0 video (interfaces 0-1), a UAC1 microphone (interfaces 2-3, mono 16-bit at 16/32/48 kHz), and a HID interface (4). They also show iConfiguration = 0, meaning no configuration name. The TV reports two interfaces and a configuration named "Brio 305", so the TV did not receive the descriptor set those PCs received. I found no documented Brio 300 mode, setting or firmware that removes the mic.

### Cited Findings
- linux-hardware.org lists 046d:0942 "Logitech Brio 300" as class 0e-01-00 (camera), seen on 11 computers. Its driver table only shows uvcvideo/usbcore matches, because it indexes by the first interface class — [linux-hardware.org device page](https://linux-hardware.org/?id=usb:046d-0942)
- Raw `lsusb -v` from four independent Linux probes (an ASUS TUF B550 desktop, a Dell OptiPlex 7010, a Framework laptop, and one more) are identical in structure — [probe 1db191b4d3](https://linux-hardware.org/?probe=1db191b4d3&log=lsusb), [probe 4259130bce](https://linux-hardware.org/?probe=4259130bce&log=lsusb), [probe 50470cfc35](https://linux-hardware.org/?probe=50470cfc35&log=lsusb), [probe ff03f6aa77 (Framework)](https://linux-hardware.org/?probe=ff03f6aa77&log=lsusb):
  - Device: bcdUSB 2.00, bDeviceClass 239/2/1 (IAD), bcdDevice 0.21, iProduct "Brio 300", bNumConfigurations 1. The device and VideoStreaming layout match what the TV shows.
  - Configuration: wTotalLength 2230, bNumInterfaces 5, **iConfiguration 0**, MaxPower 500 mA.
  - IAD 0 groups interfaces 0-1 as Video. Interface 0 is VideoControl, bcdUVC 1.00. Interface 1 is VideoStreaming with alternate settings 0-7, which matches the TV's "8 alternate settings". Alt 7's endpoint is wMaxPacketSize 0x13fc (3x1020 bytes), a high-bandwidth isochronous endpoint that only exists at high speed.
  - IAD 1 groups interfaces 2-3 as Audio. Interface 2 is AudioControl, bcdADC 1.00 (UAC1). Its input terminal is wTerminalType 0x0403 "Speakerphone, no echo reduction" with bNrChannels 1, and it has a feature unit with Mute and Volume. Interface 3 is AudioStreaming: alt 1 is PCM 1 ch 16-bit 32000 Hz, alt 2 is 16000 Hz, alt 3 is 48000 Hz, all on isochronous asynchronous endpoint 0x82.
  - Interface 4 is HID (class 3) with a 3-byte interrupt IN endpoint 0x84.
  - By my count of the dump, the audio IAD starts about 2011 bytes into the 2230-byte configuration. The video part is about 90% of the descriptor, and audio plus HID are the last ~220 bytes.
- Logitech spec for the Brio 300: "Single, digital noise reducing microphone", "Mic range: Up to 4m", USB-C plug-and-play, "Required: Available USB-C port". It lists Windows, macOS and ChromeOS, not Android or TV — [Logitech Brio 300 spec](https://support.logi.com/hc/en-my/articles/11403607280919-Specification-Brio-300)
- The Brio 305 (business twin) datasheet says "Audio: Single digital microphone" and gives the same 1080p/30 USB-C spec — [Brio 305 datasheet](https://www.logitech.com/content/dam/logitech/en_au/video-collaboration/pdf/brio-305-datasheet.pdf). Logitech's Brio 305 spec page gives the mic range as "Up to 4ft (1.22 m)", which conflicts with the 4 m on the Brio 300 page — [Logitech Hub Brio 305 spec](https://hub.sync.logitech.com/brio305/post/specifications---brio-305-KvlpTTrX0Fls3qx); [logitech.com Brio 305](https://www.logitech.com/en-ch/products/webcams/brio-305-webcam.html)
- Brio 300, 301 and 305 share one firmware line. Firmware 1.0.28 notes say: "Fixed the issue where mic was not working correctly", "Fixed the issue where noise could be heard while recording", "Fine-tuned audio performance as per Microsoft Teams specifications" — [Logitech Hub release note 1.0.28](https://hub.sync.logitech.com/brio305/post/brio-300-301-305-1-0-28-dNpJyKUO4eUaSK5). Logi Tune delivers these updates on Windows and macOS; it is not available for ChromeOS — [Brio 305 datasheet](https://www.logitech.com/content/dam/logitech/en_au/video-collaboration/pdf/brio-305-datasheet.pdf)
- Logitech's only documented "not recognized" cause for Brio 300/301/305 is adapters: "Some adapters only support power, in which case BRIO 300/301/305 will not be recognized" — [Logitech support](https://support.logi.com/hc/en-gb/articles/11530425232535-My-BRIO-300-301-305-1080p-Webcam-does-not-connect-or-is-not-recognized-by-my-computer). That failure removes the whole device, not only the mic.
- Logitech's Brio series comparison lists the Brio 105 and 305 with "1 Omnidirectional" mic — [Logitech Hub Brio comparison](https://hub.sync.logitech.com/mxbrio)
- Mainline Linux has a documented Logitech webcam enumeration bug. The commit adding the C920/C930e quirk says the cameras were "spewing random data (possibly some leftover UVC buffers) on the second (full-sized) Get Configuration request of the enumeration phase … it is not always recoverable. Set the USB_DELAY_INIT quirk" — [commit e0429362ab15 (2014)](https://github.com/torvalds/linux/commit/e0429362ab15c46ea4d64c3f8c9e0933e48a143a). Later commits added the C920-C and C925e — [a1279ef74eee](https://github.com/torvalds/linux/commit/a1279ef74eeeb5f627f091c71d80dd7ac766c99d), [7f038d256c72](https://github.com/torvalds/linux/commit/7f038d256c723dd390d2fca942919573995f4cfd) — and lengthened the delay because "in rare cases we still see issues" — [b2a542bbb308](https://github.com/torvalds/linux/commit/b2a542bbb3081dbd64acc8929c140d196664c406)
- Today's mainline quirk table applies USB_QUIRK_DELAY_INIT to C920 (082d), C920-C (0841), C930e (0843), C925e (085b), C922 (085c), CC3000e (0847/0848) and PTZ Pro (0853). **There is no entry for 046d:0942** — [drivers/usb/core/quirks.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/quirks.c). The quirk adds msleep(200) between the 9-byte and full-length config-descriptor reads — [drivers/usb/core/config.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/config.c) — and msleep(2000) in hub port init — [drivers/usb/core/hub.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/hub.c)

### Inferences
- The mic is a normal UAC1 function on PCs. The hardware has one, and Linux sees it on every probe I examined.
- The TV's descriptor differs from the PC's in at least two ways: it has 2 interfaces instead of 5, and a configuration name "Brio 305" where the PCs have index 0. The HID interface is also missing on the TV, so whatever happened removed everything after the video function, not just audio. The parsed configuration ends exactly where the audio IAD would start. That pattern fits either (a) a truncated or garbled full-length config read during enumeration, the documented Logitech failure, with no quirk for 0942, or (b) the camera returning a different, video-only descriptor set because of different firmware or mode. Neither is verified for the Brio 300.
- A garbled config header could explain the "Brio 305" name. The 300/301/305 share firmware, so a "Brio 305" string plausibly exists in the device's string table, and a random iConfiguration byte could point at it. This is speculative.
- USB-C vs USB-A should not matter. A passive C-to-A adapter carries the same USB 2.0 D+/D- pair. The power-only failure Logitech describes would hide the whole camera.

### Gaps
- I found no lsusb dump of a Brio 300 or 305 with newer firmware than bcdDevice 0.21. So I can't rule out that later firmware (for example 1.0.28+) changes iConfiguration or the interface layout.
- I found no report of a Brio 300 mic missing on any host (Linux, Windows, macOS, Android). There is a Windows report of a mic missing on the older Brio 4K — [r/logitech](https://www.reddit.com/r/logitech/comments/1b0y3u7/brio_webcam_microphone_not_working_with_windows_11) — a different product.
- I found no Logi Tune or Logitech Sync setting documented to disable or hide the webcam mic at the USB level.

## Q2. Could Android's USB host stack or the TV's kernel be hiding the audio interface? How to verify without root?

### Takeaway
Android 12 does not hide it. The framework builds UsbDevice from the raw bytes the kernel cached at enumeration, and its only interface filter is hard-coded off; it would only drop AudioStreaming interfaces anyway, not AudioControl or HID. So the two-interface view is what the TV's kernel received from the camera. Root is not needed to see exactly what was received: `dumpsys usb dump-descriptors -dump-raw`, logcat, UsbManager, and probably sysfs will tell a short or garbled read apart from a genuinely video-only descriptor.

### Cited Findings
- Android 12 `UsbConfigDescriptor.toAndroid()` filters interfaces only when `mBlockAudio` is true. The field is declared `private boolean mBlockAudio; // leave it off for now. We be replace with a "Developer Option"` and is never set. When set, it drops only class 1 / subclass AudioStreaming interfaces. The configuration name comes from `parser.getDescriptorString(mConfigIndex)`, i.e. iConfiguration — [UsbConfigDescriptor.java (android12-release)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/descriptors/UsbConfigDescriptor.java)
- libusbhost reads the descriptors by `read(fd, device->desc, sizeof(device->desc))` on the usbfs node, into a 4096-byte buffer (`MAX_DESCRIPTORS_LENGTH 4096`). The Brio's 18 + 2230 bytes fit, so this is not a userspace truncation. `usb_device_get_string` returns nothing for string id 0, so a non-empty configuration name means the received iConfiguration was non-zero — [libusbhost usbhost.c](https://android.googlesource.com/platform/system/core/+/refs/heads/android12-release/libusbhost/usbhost.c)
- Linux docs say reading a usbfs device file returns "first the device descriptor, then the descriptors for each configuration … If a device returns less configuration descriptor data than indicated by wTotalLength there will be a hole in the file" — [Documentation/driver-api/usb/usb.rst](https://github.com/torvalds/linux/blob/master/Documentation/driver-api/usb/usb.rst). `usbdev_read()` copies `dev->rawdescriptors[i]` and skips the unallocated parts — [drivers/usb/core/devio.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/devio.c)
- In the kernel, a short read logs "config index %d descriptor too short (expected %i, got %i)" and parses only the bytes received. A count mismatch logs "config %d has %d interface%s, different from the descriptor's value" — [drivers/usb/core/config.c](https://github.com/torvalds/linux/blob/master/drivers/usb/core/config.c). These are kernel messages, and dmesg normally needs root on production Android.
- `UsbHostManager.usbDeviceAdded()` denies only whole devices: hubs, HID-boot class, address deny-list (`config_usbHostDenylist`), or per-interface devices whose interfaces are ALL deny-listed. It does not remove individual interfaces. It logs `"USB device attached: vidpid %04x:%04x mfg/product/ver/serial … hasAudio/HID/Storage: %b/%b/%b"` — [UsbHostManager.java (android12-release)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/UsbHostManager.java)
- `dumpsys usb dump-descriptors` supports `-dump-short`, `-dump-tree`, `-dump-list` and `-dump-raw` for the LAST connected USB device. `-dump-raw` prints "Raw Descriptors N bytes" as hex — [UsbService.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/UsbService.java); [UsbHostManager.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/UsbHostManager.java)
- `UsbDevice.toString()` (which dumpsys prints) includes `mVersion` (bcdDevice), `mHasAudioPlayback`, `mHasAudioCapture`, `mHasVideoCapture` and the full configuration and interface list — [UsbDevice.java (android12-release)](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/core/java/android/hardware/usb/UsbDevice.java)
- The descriptor parser catches per-descriptor exceptions and logs `"Exception parsing USB descriptors. type:0x…"` under tag `UsbDescriptorParser` — [UsbDescriptorParser.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/descriptors/UsbDescriptorParser.java)
- UsbAlsaManager's audio deny-list in Android 12 contains only two Sony PS4 controllers, and only for output — [UsbAlsaManager.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/UsbAlsaManager.java)

### Inferences
- **No-root checks**, in order:
  1. Replug the Brio, then run `adb shell dumpsys usb dump-descriptors -dump-raw` and `-dump-list`. Bytes 18-26 are the config header. wTotalLength at offset 20-21 should be 0xB6 0x08 (2230) on PC firmware, bNumInterfaces at offset 22 should be 5, and iConfiguration at offset 24 should be 0.
     - Header says 2230 and 5, but bytes stop or turn to zeros or garbage near offset ~2029: the read was short or garbled (enumeration glitch).
     - Header itself says 2 interfaces and a smaller wTotalLength: the camera served a video-only configuration (firmware or mode).
  2. `adb shell dumpsys usb | grep -A3 0942`: read mVersion (bcdDevice; Linux probes show 0.21), mHasAudioCapture, and the VideoStreaming alt 7 endpoint's max packet size. 0x13fc (5116) means a high-speed link; a full-speed "other speed" configuration would differ.
  3. `adb logcat -b all -d | grep -E "USB device attached|UsbDescriptorParser|UsbAlsaManager"` right after replugging.
  4. Probably works but unverified (Sony's SELinux policy may block shell reads): `adb shell 'for d in /sys/bus/usb/devices/*; do [ -f $d/idProduct ] && echo $d $(cat $d/idVendor):$(cat $d/idProduct) speed=$(cat $d/speed) nif=$(cat $d/bNumInterfaces) bcd=$(cat $d/bcdDevice) cfg=$(cat $d/configuration 2>/dev/null); done'`.
  5. From any app, without permission: `UsbManager.getDeviceList()`, then for each `UsbDevice` call `getConfigurationCount()`, `getConfiguration(i).getInterfaceCount()` and `getInterface(j).getInterfaceClass()`. With user-granted permission, `UsbDeviceConnection.getRawDescriptors()` returns the same bytes.
- **Repeatability test.** Plug and unplug the Brio 5-10 times. Also try each TV USB port, a full mains power-cycle of the TV, and plugging in after the TV has fully booted. If the interface count ever changes, it is an enumeration race like the C920 bug. This would fit the earlier "camera plus USB audio" observation. A powered USB 2.0 hub in between sometimes changes timing too (unverified).
- **Cross-check on the user's Mac.** `system_profiler SPUSBDataType` shows the Brio's "Version" (bcdDevice). `system_profiler SPAudioDataType` should list a "Brio 300" input. `ioreg -p IOUSB -l -w0 | grep -A40 "Brio 300"` shows the details. Logi Tune for Mac can update the firmware to the current 300/301/305 release before re-testing on the TV.
- A kernel-level hide on the TV is unlikely. usbfs serves the raw cached bytes whether or not drivers bind, and Android parsed the video function fine. A Sony kernel patch that rewrites cached descriptors is theoretically possible but I found no evidence of one.

### Gaps
- Not verified on this TV: the raw descriptor bytes, the bcdDevice, the link speed, and whether the result varies across replugs. The Sony kernel version and whether it carries any Logitech quirk are also unknown.
- No source confirms whether Android 12 shell can read `/sys/bus/usb/devices/*` on Sony BRAVIA firmware.

## Q3. Is the Brio 300 microphone format compatible with Android's USB audio HAL?

### Takeaway
Yes, once it enumerates. It is a plain UAC1 mono 16-bit mic at 16, 32 or 48 kHz, which Linux snd-usb-audio and Android's ALSA profile code both handle. Android would classify it as "USB Device In" rather than "USB Headset In". Both are in the TV's usb_audio_policy_configuration.xml.

### Cited Findings
- Brio 300 mic format: UAC1 (bcdADC 1.00), PCM, 1 channel, 16-bit subframes, discrete 32000, 16000 and 48000 Hz alternate settings, async isochronous IN — [linux-hardware probe ff03f6aa77](https://linux-hardware.org/?probe=ff03f6aa77&log=lsusb)
- Android's ALSA device profile probes `std_sample_rates[] = {96000, 88200, 192000, 176400, 48000, 44100, 32000, 24000, 22050, 16000, 12000, 11025, 8000}` and channel counts from 24 down to 1 — [alsa_device_profile.c (android12-release)](https://android.googlesource.com/platform/system/media/+/refs/heads/android12-release/alsa_utils/alsa_device_profile.c)
- `UsbDescriptorParser.hasInput()` treats any input terminal whose category is not USB-undefined (0x01xx) or output (0x03xx) as input. 0x0403 is in the 0x04xx bidirectional category, so it counts. `hasMic()` and the headset heuristic look only for 0x0201 (mic), 0x0402 (headset), 0x0400 and 0x0603 — [UsbDescriptorParser.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/descriptors/UsbDescriptorParser.java). AOSP's USB headset spec expects headsets to report 0x0402 — [AOSP USB headset spec](https://source.android.com/docs/core/interaction/accessories/headset/usb-headset-spec)
- In Android 12, UsbAlsaManager registers a USB audio device only if ALSA has a card for it. It runs in single-device mode (`mIsSingleMode = true`): a newly attached USB audio device deselects the previous one. It skips routing entirely if `Settings.Secure usb_audio_automatic_routing_disabled` is non-zero — [UsbAlsaManager.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/services/usb/java/com/android/server/usb/UsbAlsaManager.java); [Settings.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/android12-release/core/java/android/provider/Settings.java)
- AOSP: on Android 12, "Routing to multiple USB devices simultaneously is not supported". Android 14 adds multiple USB devices of different types — [AOSP combined audio device routing](https://source.android.com/docs/core/audio/combined-audio-routing)
- Mainline snd-usb-audio applies a vendor-wide Logitech flag (`VENDOR_FLG(0x046d, QUIRK_FLAG_CTL_MSG_DELAY_1M)`) and device-specific flags for older webcams. There is no 0942-specific entry — [sound/usb/quirks.c](https://github.com/torvalds/linux/blob/master/sound/usb/quirks.c)

### Inferences
- Format is not the blocker. The blocker is that the TV never received, or never kept, the audio interface descriptors. If a replug ever exposes them, Android should create an `AUDIO_DEVICE_IN_USB_DEVICE` at 48 kHz mono with no app changes.
- Practical rule on Android 12: only one USB audio device is active, the last one plugged in. If both the Brio's mic and a USB speakerphone ever enumerate, plug the speakerphone last. Check `adb shell settings get secure usb_audio_automatic_routing_disabled` returns null or 0.

### Gaps
- Not checked: whether the TV's older kernel (exact version unknown) lacks the vendor-wide Logitech CTL_MSG_DELAY quirk, and whether that matters for the Brio's UAC controls.

## Q4. Workarounds: USB mics and speakerphones, hubs, Bluetooth, remote mic, phone as mic, TV built-in mic

### Takeaway
The most reliable fix is a class-compliant USB speakerphone with on-board echo cancellation: about ₹5,800 (EMEET M0 Plus) to ₹14,000 (Jabra Speak 510). It works only if Android routes the call audio OUT through the speakerphone's own speaker, which must be checked on this Sony. A ₹1,000-2,000 USB lavalier or desk mic is the cheapest fix, but leaves echo handling to software. Bluetooth headset mics and the remote's mic are not viable or are unverified. A phone-as-mic is possible only through custom code in the user's own WebView app.

### Cited Findings

### Inferences
- **Recommended setup.** Keep the Brio on one TV USB port for video. Add a USB speakerphone (EMEET M0 Plus at ₹5,799 for value, or a Jabra Speak 410/510 for proven AEC) on another port. Plug the speakerphone in last (Android 12 single-USB-audio rule).
  - Then verify output routing during a call: `adb shell dumpsys media.audio_policy` should show USB Device Out among available outputs, and `adb shell dumpsys audio` should show the call stream's device. The speakerphone's AEC only cancels audio it plays itself. If the TV keeps playing call audio through its own speakers, the speakerphone hears the TV and echo remains.
  - If the TV's usb_audio_policy_configuration.xml has no "USB Device Out" or "USB Headset Out" devicePort, Android cannot route output there. The notes list only "USB Device In" and "USB Headset In"; whether Out ports exist is unverified.
  - The app can force routing with `AudioManager.setCommunicationDevice()` (API 31) for MODE_IN_COMMUNICATION. Chromium already calls `setMode(MODE_IN_COMMUNICATION)` and `setCommunicationDevice` — [AudioManagerAndroid.java](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/base/android/java/src/org/chromium/media/AudioManagerAndroid.java).
- **Cheapest setup.** A Boya BY-LM40 (₹1,859) or K669B-class USB mic works as "USB Device In". Echo then depends entirely on software AEC (Q5), so keep TV volume moderate and put the mic near the speaker's mouth, away from the TV speakers. A lavalier clipped on the user reduces echo pickup a lot.
- **Hubs.** The Brio declares 500 mA MaxPower; speakerphones without batteries draw similar current. With only one free TV port, a *powered* USB 2.0 hub is safer than an unpowered one. This is my inference: I found no Sony VH21 port-current spec. The C-to-A adapter on the Brio is fine if it carries data.
- **Bluetooth headset mic.** Unverified and likely unsupported. Sony and Google document only A2DP output. Using a headset mic needs the TV to act as the HFP/HSP audio gateway with SCO input. Check with `adb shell dumpsys bluetooth_manager | grep -i -E "HeadsetService|hfp"` and look for AUDIO_DEVICE_IN_BLUETOOTH_SCO_HEADSET in `dumpsys media.audio_policy`. Even if it works, SCO is 8/16 kHz narrow or wideband and suspends A2DP. Low priority.
- **Remote mic.** Not usable for calls, per Google's own statement above.
- **TV built-in mic.** If the VH21 is a model with a built-in far-field mic and the switch is on, check whether AUDIO_DEVICE_IN_BUILTIN_MIC appears as an available input in `dumpsys media.audio_policy`. Whether third-party apps can capture from it is unknown (see Gaps).
- **Phone as wireless mic.** Without root, no app can create a system-wide virtual mic on Android. But the tvchat WebView already injects JS at document start, so it could override `navigator.mediaDevices.getUserMedia` to return a MediaStream whose audio track comes from a phone's browser page over a local WebRTC connection. The phone would do its own noise suppression.
  - Caveats: the phone's AEC has no reference for the TV speaker output, so echo remains unless the phone is close to the talker. It adds latency and complexity.
  - This is an engineering inference; nobody I found has done it for WhatsApp Web.

## Q5. Echo cancellation on Android TV: WebView/WebRTC AEC, AcousticEchoCanceler, and why a speakerphone with on-board AEC is usually the better answer

### Takeaway
In Android WebView (Chromium), getUserMedia's echoCancellation uses the platform AEC only if `AcousticEchoCanceler.isAvailable()` is true. Otherwise it falls back to WebRTC's software AEC, which only has a reference signal for audio played through RTCPeerConnection. TVs often lack a platform AEC. WhatsApp Web's calling engine needs SharedArrayBuffer, so it probably runs its own engine, and whether its playback reaches that reference is unknown. The Brio's mic itself declares "no echo reduction". A speakerphone that cancels echo in its own DSP, and also plays the far-end audio, removes all of these dependencies.

### Cited Findings
- Chromium Android `GetInputStreamParameters()`: `effects = AcousticEchoCancelerIsAvailable() ? ECHO_CANCELLER : NO_EFFECTS`, and the Java side returns `AcousticEchoCanceler.isAvailable()` — [audio_manager_android.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/audio/android/audio_manager_android.cc); [AudioManagerAndroid.java](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/base/android/java/src/org/chromium/media/AudioManagerAndroid.java)
- Blink's `EchoCanceller::GetPreferredAec()`:
  - picks `kPlatformProvided` if the device reports ECHO_CANCELLER;
  - else `kChromeWide` if chrome-wide AEC is enabled;
  - else `kPeerConnection`.
  
  The APM runs in the renderer for PeerConnection and PlatformProvided types — [media_stream_audio_processor_options.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/platform/mediastream/media_stream_audio_processor_options.cc); [media_stream_constraints_util_audio.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc)
- A Chromium engineer wrote: "On Android, Chrome can utilize built-in AEC components (not part of actual Chrome but the Android platform) and therefore cancel all echo. However, HW AECs are not supported on all devices; hence non-WebRTC audio will leak on those." Users in the thread report that browser AEC doesn't cancel audio played via the Web Audio API — [Chromium issue 40504498](https://issues.chromium.org/issues/40504498)
- Android platform AEC can silently fail in Chrome. With AAudio input, Chrome "believes AEC is enabled, but no effect is applied" (2023; fixed using AAUDIO_INPUT_PRESET_VOICE_COMMUNICATION). Chromium also disables AAudio input on Unisoc Android 11 and below for "missing/broken echo cancellation" — [Chromium issue 40941629](https://issues.chromium.org/issues/40941629); [audio_manager_android.cc](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/media/audio/android/audio_manager_android.cc)
- WebRTC's Android audio code avoids the AOSP software AEC and NS UUIDs, treating them as undesirable, and checks `EFFECT_TYPE_AEC` availability — [WebRtcAudioEffects.java](https://chromium.googlesource.com/external/webrtc.git/+/HEAD/modules/audio_device/android/java/src/org/webrtc/voiceengine/WebRtcAudioEffects.java)
- The Brio 300's own input terminal type is 0x0403 "Speakerphone, no echo reduction". The UAC terminal types distinguish this from echo-suppressing and echo-cancelling speakerphones — [linux-hardware probe ff03f6aa77](https://linux-hardware.org/?probe=ff03f6aa77&log=lsusb)
- Jabra Speak 410/510 do "In-built echo cancellation"; EMEET M0 Plus "eliminates echos of the speaker" — [Jabra 410 techsheet](https://www.jabra.com/_/media/Jabra_VXi_Product-Documentation/Jabra-SPEAK-410-Series/technical-specifications/RevB/Jabra-Speak-410-Techsheet-A4-290420-Web.pdf); [Amazon.in EMEET M0 Plus](https://www.amazon.in/Conference-Speakerphone-Reduction-Bluetooth-Compatible/dp/B0BVZLS5GZ)
- WhatsApp warns that separate external mic and speaker devices "might cause an echo" with Web calling. Its 2026 Web calling launch added in-call noise suppression — [WhatsApp Help](https://faq.whatsapp.com/2092488194268012); [WhatsApp blog](https://blog.whatsapp.com/introducing-web-calling-on-whatsapp-plus-more-new-updates)
- A practitioner cheat sheet (vendor PDF, medium reliability) says Android AcousticEchoCanceler "quality varies wildly by device model". It warns that stacking two cancellers can produce half-duplex "walkie-talkie" audio, and recommends running exactly one — [WebRTC Echo Cancellation cheat sheet](https://cdn.prod.website-files.com/64e8910adc5a63966a68acea/6a21c5170c93af2bcdf13b91_6a21c5151e697d8889816c5b_webrtc-echo-cancellation-integration-cheat-sheet.pdf)

### Inferences
- **Check on the TV first.** In tvchat's Java code, log `AcousticEchoCanceler.isAvailable()` and `NoiseSuppressor.isAvailable()`. Also `adb shell dumpsys media.audio_flinger | grep -i -A3 -E "aec|echo"` and `adb shell cat /vendor/etc/audio_effects.xml` (look for a `<preprocess>` stream with an aec effect). On TVs with no voice-call use case, these are often absent (unverified for this Sony). If absent, WebView uses the WebRTC software AEC (kPeerConnection).
- **Whether software AEC helps depends on WhatsApp.** It helps only if WhatsApp Web plays far-end audio through an RTCPeerConnection audio track. WhatsApp's need for SharedArrayBuffer (project notes) suggests a WASM engine that may render through Web Audio. In that case the browser AEC has no reference, and only WhatsApp's own in-WASM processing (if any) would cancel echo. Test empirically: call a phone, have the far end talk, and listen for their voice coming back.
- **Software AEC is harder on this TV.** Sony's output pipeline (the "aud_cpupost" post-processing seen in the call CPU profile) and TV speaker latency are likely nonlinear and long. That weakens any software AEC whose reference is taken before the TV's processing.
- **Why a speakerphone is the better answer.** The speakerphone's DSP sees both its own speaker drive signal and its mics with fixed, short, known latency, so it needs no help from Android, WebView or WhatsApp. That holds only if the call audio actually plays through the speakerphone (Q4 routing caveat).
  - With such a device, consider `echoCancellation: false` in tvchat's getUserMedia constraints (keep `noiseSuppression` optional) to avoid double processing. Compare both settings on real calls.
  - Today tvchat turns processing off when no USB mic is present and on when one is (project notes). Revisit that switch per device type: plain mic means software AEC on; AEC speakerphone means test with it off.
- **With a plain USB mic and TV speakers.** Keep echoCancellation on, lower TV volume, and use a close-talk lavalier. Expect occasional echo or ducking, consistent with WhatsApp's own warning.
